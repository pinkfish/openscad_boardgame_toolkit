# OpenSCAD Board Game Toolkit Constitution

## Core Principles

### I. Developer Experience First

Every public API MUST prioritize usability and speed of box creation. The user
must be able to create a complete box (body, lid, compartments) with minimal
keystrokes. This means:

- Dimensions, thicknesses, and styling MUST be specifiable once and
  automatically propagated to every component that needs them -- the user never
  retypes the same value.
- Sensible defaults MUST be provided for every parameter so a minimal
  specification produces a usable result.
- The fluent builder API MUST support method chaining so the entire
  configuration reads as a single expression.
- Error messages MUST name the field that is wrong and the valid range or
  expected type, not the internal function that detected it.
- Breaking changes to public APIs MUST NOT be made without a migration path.

### II. Single Source of Truth

Every dimensional, positional, and decorative parameter MUST have exactly one
canonical home. Duplication breeds drift:

- `BoxSpec` is the one frozen configuration for a box; box types read from it
  and never cache derived dimensions in mutable state.
- The `Interior` frame (origin, size, region) is the ONE source the pipeline
  uses to place contents, compute hollowing masks, and clip cavities. No box
  type may re-derive `inner_width`/`inner_length`/`inner_height` independently.
- A lid's decoration is described by the single `Lid` object on `BoxSpec.lid`;
  there MUST NOT be separate fields for label text, shape image, or pattern
  that require reconciliation at build time.
- Per-type options are a `BoxTypeOptions` dataclass named by the type's
  `options_class`; `BoxSpec` validates the match at construction so the wrong
  options class cannot reach a box type silently.

### III. Performance by Design

The toolkit MUST be fast in the edit-run cycle. Geometry generation is
inherently expensive (CSG boolean chains, meshing), so the system caches
aggressively:

- Layout computations (bin-packing, compartment arrangement) MUST be cached so
  repeated renders of the same configuration reuse prior results.
- The interior frame and derived properties MUST be computed once and cached at
  first access, not recomputed on every property read.
- Geometry construction MUST defer to native CSG operations (pybosl2) over SDF
  (frep/libfive) unless a shape has no CSG equivalent. SDF meshing is ~10-20x
  slower and MUST be reserved for shapes that genuinely require it (e.g.
  convex_polyhedron).
- Test suites MUST be tiered: a fast pass (~1.5s, pure Python, no subprocess
  app) for the inner loop, and a full pass (~6 min, with the real render app)
  for pre-commit verification.

### IV. Test-First

All code MUST be tested. This is non-negotiable:

- New features MUST include both a pure-Python unit test (fast suite) and, for
  geometry-generating code, a render test that shells out to PythonSCAD and
  verifies real faceted output.
- Geometry tests MUST assert measurements (bounding boxes, positions) rather
  than facet counts. A wrong offset or a part below the print bed can produce
  the same facet count as the correct geometry.
- The fast test suite (`python3 tests/run_fast.py`) MUST pass before any commit.
- The full test suite (`python3 -m unittest discover -s tests`) SHOULD be run
  before pushing or opening a pull request.
- Regression tests MUST accompany bug fixes -- a test that reproduces the
  defect and fails before the fix is applied.

### V. Documented by Default

Every public module, class, function, and dataclass field MUST be documented:

- Module-level docstrings MUST state the module's purpose, its key exports,
  and the general usage pattern.
- Every public function and method MUST have a docstring describing parameters,
  return value, and any raised exceptions.
- Every dataclass field MUST have a docstring or an inline comment explaining
  its meaning, valid range, and default rationale.
- User-facing features MUST have a corresponding wiki tutorial or example so
  a new user can discover and use the feature without reading source code.
- The `docs/` directory and wiki MUST be regenerated by the CI toolchain so
  they never fall out of sync with the source.
- Internal helpers and private methods are exempt from docstring requirements
  but MUST still have descriptive names.

## Quality Gates

Before code enters the repository it MUST pass:

- **Tests**: The fast test suite MUST pass (see Principle IV). Render tests are
  required for geometry-generating changes and MUST pass when the PythonSCAD
  binary is available.
- **Type checking**: `npx pyright <file>` MUST report zero NEW errors. The
  repository has a baseline of ~48 known infrastructure errors (PythonSCAD
  native symbols invisible to the type checker). Compare against the baseline,
  not zero.
- **Linting**: `ruff check` MUST report no issues on changed files. Ruff is
  configured for Python 3.11 with rules E, F, and I (pycodestyle, Pyflakes,
  isort).
- **Imports**: Every import MUST be explicit. Wildcard imports (`from X
  import *`) are forbidden except in test render harness script strings where
  the namespace is an eval environment for arbitrary expressions.
- **License header**: Every new source file MUST carry the Apache-2.0 license
  header.

## Development Workflow

1. **Specify**: New features start as a spec (`/speckit.specify`) defining
   user stories, functional requirements, and measurable success criteria.
2. **Plan**: The spec is broken into a technical plan (`/speckit.plan`)
   mapping requirements to implementation artifacts.
3. **Implement**: Code is written against the plan, with tests written first.
   The fast test suite validates each change incrementally.
4. **Verify**: Before marking work complete, run the full test suite and type
   check. Render tests must confirm geometry correctness.
5. **Document**: Update relevant documentation and examples as part of the
   feature, not as a separate task.

## Governance

This constitution supersedes all other development practices for this project.
Any deviation MUST be justified in writing (a code comment or commit message)
and is subject to review.

- **Amendments**: Changes to this constitution require a pull request that
  documents the rationale, impact on existing code, and any migration steps.
  The version MUST be incremented per semantic versioning rules:
  - MAJOR: Principle removals or redefinitions that invalidate existing
    practices.
  - MINOR: New principles or materially expanded guidance.
  - PATCH: Clarifications, wording, typo fixes.
- **Compliance**: All code reviews and pull requests MUST verify compliance
  with the active constitution. Complexity that violates a principle MUST be
  explicitly justified.
- **Runtime guidance**: The `CLAUDE.md` file provides development environment
  specifics, command references, and hard-won constraints. It is the living
  companion to this constitution.
